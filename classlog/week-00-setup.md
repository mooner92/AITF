## 2026-08-16 · 서버 실사 + 계획 수립

수업 서버로 쓸 기존 OCI 인스턴스를 실사하고 세팅 계획을 스펙(specs/)으로 정리했다.

**실사에서 배운 것 (계획이 3번 바뀐 이유):**

1. "인스턴스 리사이즈가 필요하다"고 알고 있었는데, 메타데이터를 조회해 보니 이미 무료 한도 최대 셰이프(4 OCPU/24GB)였다. → 추측 말고 `curl`로 메타데이터를 직접 확인할 것.
2. 루트 디스크가 96% 차 있어서 큰일 난 줄 알았는데, `lsblk`를 보니 부트 볼륨 200G 중 155G가 파티션 밖에 미할당 상태였다. → 콘솔 작업 없이 서버 안에서 확장 가능. "디스크 부족"과 "볼륨 부족"은 다른 문제다.
3. 이 서버는 전용이 아니라 기존 서비스가 함께 도는 공용 서버다. → 두 가지 설계 변경: ① 127.0.0.1 바인딩만으로는 로컬 계정(학생)을 못 막으므로 내부 서비스에 인증 추가 ② 부하 테스트 통과 기준에 "기존 서비스 무영향" 추가.

**오늘 한 것:** 저장소 개설, 공개/비공개 2-존 정책(SECURITY.md) + pre-commit 시크릿 스캔 훅, specs 000~100 작성, 운영 스크립트 공개 버전 작성.

**다음:** 부트 볼륨 백업(운영자) → 디스크 확장 → P1 잔여 → P2 접속 경로.

## 2026-08-17 · 터널 연결 — 모니터링·Git이 도메인으로 열렸다

기존 터널이 "로컬 관리형"이라 대시보드가 아닌 서버의 설정 파일로 라우팅을 추가했다. 모니터링(OpenObserve)과 Gitea 두 개를 각각 서브도메인에 붙였고, 기존 서비스는 회귀 테스트 10/10 정상.

**작업하며 발견한 것 2개 — 둘 다 그냥 지나쳤으면 사고였다:**

1. **같은 터널에 replica가 2개 붙어 있었다.** 하나는 시스템 서비스, 다른 하나는 수개월 전 수동 실행돼 잊힌 고아 프로세스였는데, 이쪽이 `--url` 플래그로 돌고 있었다. 이 플래그는 **호스트명을 무시하고 모든 요청을 한 서비스로 보낸다**. 새 주소를 추가했어도 요청의 절반은 엉뚱한 앱으로 갔을 것이고, "가끔 안 돼요"라는 최악의 증상이 됐을 것이다. 정리 후 커넥터 1개로 통일.
2. **`ssh` 서브도메인 레코드가 이미 존재했다.** 규칙을 켜는 순간 인증 없이 SSH가 열릴 수 있어 즉시 규칙을 껐다. 확인해 보니 그 주소는 우리 터널이 아닌 다른 곳을 가리키고 있어 실제 노출은 없었지만, "DNS는 내가 만든 것만 있다"는 가정이 틀릴 수 있다는 걸 배웠다.

교훈: 라우팅을 바꾸기 전에 **누가 이미 그 이름을 쓰고 있는지, 누가 이미 그 터널에 붙어 있는지** 먼저 본다.

**다음**: Cloudflare Access 정책 생성(운영자) → 그 다음에야 ssh 규칙을 켠다.

## 2026-08-18 · 모델 스택 확정 — 라우팅이 안 되는 조합을 걸러냈다

12주 비용을 벤더별로 비교하다가, **가격보다 먼저 확인했어야 할 것**을 놓치고 있었다는 걸 발견했다.

원래 계획은 "기본 모델 + 다른 벤더의 경량 모델"이었다. 그런데 두 CLI는 **별개 프로세스**다. 한 세션 안에서 "이 작업만 저쪽으로" 보내는 설정이 존재하지 않는다. 학생이 도구 두 개를 번갈아 쓰는 형태가 될 뿐이고, 그러면 10주차 리빌의 전제("네가 모르는 새 내가 갈라놨다")가 통째로 무너진다. 가격표를 세 번 비교하는 동안 이걸 안 봤다.

게다가 확인해 보니 **웹 검색은 CLI에 내장**돼 있었다. 외부 모델에 맡기려던 일을 이미 하고 있었던 것.

그래서 **같은 벤더의 두 티어**로 정리했다. 기본은 저가 티어, 어려운 문제는 하위 에이전트가 중간 티어로. 한 CLI 안에서 진짜로 라우팅되고, 키도 대시보드도 하나다. 10배 가격차가 리빌·11주차 개선 레버·12주차 절감률의 재료가 된다.

**설정은 추측으로 쓰지 않았다.** CLI에 `--strict-config`가 있어서, 후보 키를 하나씩 넣고 파서가 거부하는지 확인했다. 처음엔 대조군(엉터리 키)까지 통과해서 검증이 되는 줄 알았는데, 전체 출력을 보니 내 grep 패턴이 틀렸던 것이었다 — "unknown field"가 아니라 "unknown configuration field". 패턴을 고치니 엉터리 키는 정확히 거부됐다. **검증기가 통과했다고 믿기 전에 검증기가 실패도 잡는지 확인해야 한다.**

학생 관점 5종 재검증(실행/읽기/수정거부/git 미포함/config 쓰기가능) 통과. config를 학생 소유 600으로 둔 건 의도적이다 — 12주차에 학생이 직접 고쳐서 그래프를 내려야 하니까.

## 2026-08-18 · 접속 설계 변경 — 원천 차단에서 "선택적 개방"으로

운영자가 좋은 질문을 했다. "토큰 사용량이 이미 추적되고 있는데, 굳이 어렵게 갈 필요가 있나? 집에 가서 또 세팅하려면 귀찮아서 학생들이 안 할 텐데."

맞는 지적이었다. 원래 설계는 학원 IP만 통과시키고 외부를 원천 차단하는 것이었는데, 그 전제가 만들어진 시점에는 관측이 없었다. 지금은 학생별 토큰·리소스·진도가 15분 주기로 잡히고, 비용 상한은 API hard cap이 독립적으로 막는다. **외부 접속을 원천 차단해야 할 근거가 약해진 것이다.**

그래서 정책을 두 개로 나눴다. 학원 IP는 통과(수업 중 로그인 화면 없음), 그 외에는 이메일 OTP(원하는 학생만 등록). 학원 IP는 여전히 필요하지만 **이유가 바뀌었다** — 보안 경계가 아니라 수업 중 마찰 제거용이다. 12명이 14시에 동시에 로그인 화면을 만나면 첫 10분이 날아간다.

이메일을 전원에게 받지 않고 **선택**으로 둔 건 중등반에 만 14세 미만이 포함될 수 있어서다. 커리큘럼이 GitHub를 피한 것과 같은 이유.

한 가지는 지키기로 했다. **집 접속을 허용하는 것과 숙제를 거기에 의존시키는 것은 다르다.** 숙제 원칙("서버 접속 불필요, 종이나 폰으로 5~10분")은 그대로 둔다. 전제로 삼는 순간 "컴퓨터 학원은 학생에게 2~3순위"라는, 운영자가 처음에 세운 원칙이 무너진다.

부수적으로 확인된 것: `ssh` 서브도메인은 다른 서버가 쓰는 레코드였다. 수업용은 `sshopc`로 분리한다.

## 2026-08-18 · 수업계획서 개정 — 숙제 폐지, 레드팀 교체, 참여 방법 명시

학원 제출용 계획서를 쓰면서 운영자가 세 가지를 지적했고, 셋 다 설계를 개선하는 방향이었다.

**1. 숙제를 없앴다.** 원래도 "5~10분, 종이·폰으로 가능, 안 해와도 지장 없음"이었지만, 그 정도면 계획서에 굳이 남길 이유가 없다. 더 중요한 건 **숙제가 있는 순간 안 해온 학생이 생기고 수업이 두 갈래로 갈라진다**는 것. 숙제가 하던 역할(다음 주 재료 준비)은 전부 해당 주차의 마무리 블록이나 다음 주 도입 블록으로 흡수했다. 예를 들어 "마켓에서 스킬 하나 찾아오기"는 6주차 도입 15분 블록이 됐다.

**2. 레드팀 데이를 신뢰성 점검으로 교체했다.** 운영자 지적이 정확했다 — 프롬프트 인젝션·탈옥은 **정답이 없어서 채점이 안 되고**, 가르치기도 어렵고, 청소년 대상으로 윤리 회색지대가 있다.

같은 교훈("AI는 틀릴 수 있다 → 그래서 방어한다")을 정답이 명확한 형태로 바꿨다. 짝과 AI를 교환해 **자료에 답이 없는 질문 10개**를 던지고, "모른다"고 하면 통과, 그럴듯한 거짓말을 하면 실패로 기록한다. 점수는 10점 만점. 자기 AI로 돌아와 고치고 재검사한다. 채점이 되고, 8주차 품질 개선과 9주 아레나 방어율에 그대로 이어진다. 원래 것보다 나은 블록이 됐다.

**3. 참여 방법 절을 추가했다.** 학원과 학부모가 가장 먼저 묻는 질문("뭘 설치해야 하나요?")에 대한 답이 계획서에 없었다. 5단계 흐름(브라우저 → 주소 → 터미널 → 아이디 → 지난주 작업 그대로)과, 흔한 문제 5가지가 이 구조에서 왜 안 생기는지를 표로 넣었다.

교훈: **문서를 쓰다 보면 설계의 빈틈이 드러난다.** 세 지적 모두 계획서를 쓰지 않았으면 개강 후에 발견했을 것들이다.

## 2026-08-18 · 커리큘럼 v7 — 12주 프로젝트에서 주간 스킬 위크로

운영자가 방향을 틀었다. "12주 내내 하나의 프로젝트를 파는 것보다, 기초를 가르친 뒤 매주 재밌는 스킬 하나로 실제 쓸 만한 걸 만드는 게 낫겠다. 그림, 발표자료, 이야기책, 영상 같은 것." 그리고 이 전환이 직전 고민(각자 주제 → 관리 불가)을 프로젝트 통일보다 더 근본적으로 해결한다는 걸 알게 됐다.

**주간 완결형의 힘**: 매주 전원이 같은 스킬로 같은 형태의 결과물을 만들면 — 내용만 각자 — 시연이 성립하고, 에러가 같아서 한 번 설명하면 되고, 짝이 서로 도울 수 있다. 게다가 결석 부담이 급감한다. 12주짜리 프로젝트에서 한 주를 놓치면 계속 뒤처지지만, 주간 완결형에서는 그 주 것만 놓친다.

**소유감은 "작품관"이 담당한다**: 2주차에 개인 웹페이지를 만들고 매주 결과물을 전시한다. 발산 없이(구조는 전원 동일) 소유감을 만드는 장치. 8주차에 완성해서 가족·친구에게 링크로 자랑한다.

**살아남은 것들**: 프롬프트 골프, 10주 리빌(하네스는 인프라 기반이라 프로젝트가 바뀌어도 그대로 성립 — "모델이 왜 두 개죠?" 미스터리 유지), 12주 1차vs2차 스프린트, 숙제 없음. RAG는 12주 뼈대에서 11주차 "신기술 맛보기" 30분 데모로 축소됐다.

**기술 확인**: 이미지 생성이 CLI에 내장돼 있어(feature flag 확인) 같은 키로 과금된다 — 별도 벤더가 필요 없다. 영상은 2안 전략(슬라이드쇼 영상은 확정, AI 영상은 단가 확인 후). 새 인프라 항목 하나 추가: 학생 작품을 브라우저로 볼 수 있는 정적 페이지 서빙 — 4주차 전까지 구축.

배운 것: **커리큘럼의 관리 가능성은 주제 선택이 아니라 구조(발산 vs 완결)가 결정한다.** 지난 회의에서 "공통 주제로 통일"을 고민했는데, 진짜 답은 주기를 짧게 만드는 것이었다.

## 2026-08-18 · 작품관 서빙 구축 — 홈을 열지 않고 웹에 여는 법

커리큘럼 v7의 핵심 장치인 "작품관"(학생별 웹페이지)을 실제로 구축했다.

**설계에서 함정이 하나 있었다.** 가장 쉬운 방법은 nginx가 학생 홈의 폴더를 직접 읽는 것인데, 학생 홈은 700(서로 열람 차단)이라 nginx가 못 들어간다. 홈을 711로 열면 해결되지만 — 그 순간 `.bashrc`에 든 API 키의 안전이 "파일 하나하나의 권한이 전부 올바른가"에 의존하게 된다. 한 파일만 644면 다른 학생이 키를 읽는다.

그래서 반대로 갔다: **웹에 보일 것만 홈 밖으로 꺼낸다.** 전용 웹루트를 만들고 학생 홈의 `project/public`이 거기로 심링크된다. 학생은 평소처럼 자기 프로젝트 안에서 작업하고, 홈은 700 그대로다.

**보안 검증 6종을 실측으로 통과**: 시스템 파일 심링크 차단, 타 학생 파일 심링크 차단, 자기 파일 심링크 허용, 숨김 파일 차단, 디렉토리 목록 차단, 홈 권한 유지. 특히 심링크 공격은 nginx의 소유자 검사(링크 소유자 ≠ 대상 소유자면 거부)로 막았다 — 학생이 자기 페이지에 무엇을 링크하든, 자기 소유 파일만 서빙된다.

**영상 파이프라인도 이 김에 검증**: ffmpeg(자유 빌드)를 설치하고 학생 계정에서 이미지 3장 → WebM 영상 → 웹 재생까지 확인. H.264(mp4)는 인코더 런타임 추가 설치가 필요해 확인 중 — 아이폰 공유 호환성 때문에 필요하다.

계정 생성·초기화 스크립트에 전 절차를 반영했고, 초기화가 심링크를 지키는 것까지 확인했다. 이로써 v7 신규 인프라 중 첫 항목(4주차 전 마감)이 끝났다.
