## 0. 확정 사항 (2026-08-24)

- **Slack 확정, Discord 불채택** — 수업 소통이 이미 Slack 이고(120), 도구를 하나 더
  늘릴 이유가 없다.
- **봇 이름은 바다 생물 페르소나** — `가오리` `거북이` `불가사리` 식. 모델명(qwen3.5-27B)
  대신 페르소나를 쓰는 이유:
  1. **2주차 블라인드 테스트가 공짜로 성립** — 이름이 이미 가려져 있으니 별도 마스킹이
     필요 없고, 정답 공개가 "가오리는 사실 Qwen이었다"는 장면이 된다
  2. **모델 교체가 조용히 가능** — "재료는 그 달의 최신으로 교체"(커리큘럼 원칙)할 때
     봇 이름·채널·학생의 습관은 그대로 두고 뒤의 모델만 바꾼다
  3. 중등반 친화 — 캐릭터가 있으면 말을 거는 문턱이 낮다
- **연결 모델**: 회사 서버의 Qwen 계열 + LFM 2B(경량) 등 — 서버별 포트를 열어(회사 쪽
  방화벽) OpenAI 호환 엔드포인트로 받는다. 우리 학원 서버 쪽은 아웃바운드 연결이라
  기존 "인바운드 0" 원칙 무접촉.
- **위키 기반 답변(아래 2-1)** — 이 봇들의 존재 이유. 학생이 무료 GPT(Luna)에게 물어도
  절대 나올 수 없는 답 — "우리 반이 지난주에 뭘 만들었는지" — 을 하는 봇이다.

## 목표

Slack에 `qwen3.5-27B`, `gemma-…` 같은 **모델별 봇을 하나씩** 두어,
학생이 채널에서 말을 걸면 그 모델이 답하게 한다.
2주차 블라인드 테스트(`/compare`)가 "가려놓고 맞히기"라면, 이쪽은 **평상시 상시 대화**다.

## 1. 동작 원리

### 전체 경로

```
학생: @qwen3.5-27B 이 코드 왜 안 돼?
   │
   ▼  (1) Slack이 이벤트를 봇에 전달
Slack 서버
   │  ← WebSocket (봇이 밖으로 연결. Slack이 우리를 찾아오지 않는다)
   ▼
학원 서버: 봇 프로세스 (모델당 1개)
   │  (2) 3초 안에 "받았음" 응답 + "생각 중…" 메시지 게시
   │  (3) 백그라운드로 모델 호출
   ▼  ← Zero Trust 서비스 토큰
회사 서버 A/B/C: 로컬 모델 (OpenAI 호환 API)
   │  (4) 토큰이 오는 대로 스트리밍
   ▼
   (5) 봇이 0.5초마다 chat.update 로 메시지를 덮어쓴다 → 글자가 차오르는 것처럼 보임
```

### 핵심 개념 셋

**ⓐ Socket Mode — 서버를 열지 않는다**

Slack 앱은 두 방식 중 하나로 이벤트를 받습니다.

| 방식 | 동작 | 우리에게 |
|---|---|---|
| Events API | Slack이 **우리 공개 URL로 POST** | 인바운드를 열어야 함 |
| **Socket Mode** | **봇이 Slack으로 WebSocket 연결** | ✅ **인바운드 0 유지** |

**Socket Mode를 씁니다.** 110에서 세운 "인바운드 포트를 열지 않는다"는 원칙이 그대로 지켜집니다.
봇이 밖으로 연결을 걸어 유지하는 구조라, 방화벽에 손댈 일이 없습니다.

**ⓑ 3초 규칙 — 먼저 받고 나중에 일한다**

Slack은 이벤트 전달 후 **3초 안에 응답**이 없으면 실패로 보고 재전송합니다.
로컬 모델 응답은 수 초~수십 초 걸리므로, 그대로 두면 **같은 질문에 봇이 여러 번 답합니다.**

```
1. 이벤트 수신 → 즉시 ack (1초 안에)
2. "🤔 생각 중…" 메시지를 채널에 게시 (ts 확보)
3. 백그라운드에서 모델 호출
4. 토큰이 오면 0.5초마다 chat.update 로 그 메시지를 갱신
```

이게 **ack-fast / work-slow** 패턴이며, 스트리밍 UX까지 같이 해결됩니다.

**ⓒ 봇 = Slack 앱 1개.** 모델이 3개면 앱 3개를 만들고 각각 토큰을 받습니다.
프로세스는 하나로 묶어도 되지만, **모델당 1프로세스**가 장애 격리에 낫습니다
(한 서버가 죽어도 나머지 봇은 계속 답함).

## 2. 서버 3대에 분산된 모델 연결

**전제**: 각 서버의 모델이 **OpenAI 호환 엔드포인트**(`/v1/chat/completions`)를 제공해야 합니다.
vLLM·Ollama·SGLang 전부 지원합니다. 아니면 어댑터를 하나 두어야 합니다.

```
봇 설정 (서버 /opt/scripts/bots.yaml, 600)

qwen3.5-27B:
  endpoint: https://<서버A>/v1
  model: qwen3.5-27b
  slack_app: qwen-bot          # 앱 토큰·봇 토큰은 .env 에서
gemma-…:
  endpoint: https://<서버B>/v1
  ...
```

- 학생은 **회사 서버에 직접 닿지 않습니다.** 봇 프로세스만 서비스 토큰을 가집니다
- 서버가 응답 없으면 봇이 **"이 모델은 지금 쉬는 중이에요"**를 답합니다 (에러 스택 노출 금지)
- 동시 요청은 봇에서 큐잉 — 6명이 동시에 물어도 서버가 죽지 않게

### 2-1. 위키 기반 답변 — 봇이 "우리 반을 아는" 방법

봇은 그냥 로컬 모델 중계기가 아니라 **우리 반 위키를 읽고 답하는** 존재다.
"지난주에 우리 뭐 배웠지?" "누가 급식 봇 만들었지?" 같은 질문에 답한다 —
무료 GPT 계정으로는 절대 얻을 수 없는 답이라, 로컬 모델의 존재 가치가 즉시 체감된다.

**구조 — 검색 주입(RAG), 벡터 DB 없이 시작:**

```
학생 질문 → 봇이 위키 md에서 관련 청크 검색(BM25/키워드) → 상위 2~3개를
시스템 프롬프트에 주입 → 로컬 모델이 근거 한정으로 답변 + 출처 문서 링크 병기
```

- **위키가 같은 서버에 있다** — Gitea 저장소가 로컬이라 파일 직접 읽기면 되고,
  동기화·인덱싱 파이프라인이 필요 없다. 12주 위키 전체가 수백 KB 수준이라
  벡터 DB는 과설계 — BM25 급 키워드 검색으로 충분하고, 부족해지면 그때
  임베딩(sqlite-vec)으로 승격한다
- **청크는 2~3개로 제한** — LFM 2B 같은 경량 모델은 컨텍스트가 작고 장문 주입에
  약하다. 적게 넣고 출처 링크로 보완하는 쪽이 답 품질이 높다
- **반별 위키만 읽는다** — 중등 채널의 봇은 `class-wiki-mid`만, 고등은 `-high`만
  (120의 위키 3분리와 정합). "저 사람 누구지"가 봇 답변에서도 안 나오게
- **출처 병기 필수** — 경량 모델은 여전히 지어낸다. "이 답의 근거: [w05 문서]"
  링크를 항상 붙여, 틀린 답이 나와도 학생이 원문으로 검증하는 습관까지 얻는다
- **11주차와 연결** — Gemini Notebook RAG 체험(140) 때 "너희가 매주 쓰던 가오리도
  같은 원리다"로 회수된다. 개념(청킹→검색→근거 한정 답변→출처)이 정확히 같다

### 운영 규칙 (수업용이므로 필요)

| 항목 | 값 | 이유 |
|---|---|---|
| 채널 | `#모델비교` 전용 | 다른 채널 오염 방지 |
| 호출 방식 | `@봇이름` 멘션만 | 모든 메시지에 반응하면 시끄러움 |
| 동시 처리 | 봇당 1~2건, 나머지 큐 | 로컬 GPU 보호 |
| 응답 상한 | 60초 초과 시 중단 안내 | 수업이 멈추지 않게 |
| 사용 시간 | 수업 시간 + 주중 일부 | 회사 서버 정책에 맞춤 |

## 3. 적용 가능한가 — 결론

**가능합니다.** 기술적 장벽은 없습니다. 다만 조건이 둘입니다.

| 조건 | 상태 |
|---|---|
| 각 모델이 OpenAI 호환 API 제공 | **확인 필요** (없으면 어댑터 필요) |
| 회사 서버 사용 승인 | **미승인** — 상한·시간대·로그 정책 합의 필요 |

### `/compare` 봇과의 관계 — 둘 다 만듭니다

| | `/compare` (120) | 모델별 봇 (이 문서) |
|---|---|---|
| 성격 | 가려놓고 **맞히기** | 이름 달고 **상시 대화** |
| 쓰임 | 2주차 블라인드 테스트 | 그 이후 상시 |
| 구현 | 한 프로세스가 여러 모델 팬아웃 | 모델당 1프로세스 |

**같은 백엔드 호출 코드를 공유**하므로 추가 작업은 크지 않습니다.
`/compare`를 먼저 만들고, 그 호출부를 재사용해 모델별 봇을 붙이는 순서를 권합니다.

## 4. 카카오톡 오픈채팅 — 권장하지 않습니다

조사 결과 **막힌 길**입니다.

| 방식 | 가능? | 문제 |
|---|---|---|
| 공식 오픈채팅봇 | 제한적 | 환영·알림·자동응답 3종뿐. **AI 연동 불가** |
| 카카오 오픈빌더 | ❌ | **채널(플러스친구) 전용** — 오픈채팅에 못 붙임 |
| 비공식 (메시지 감지) | ⚠️ | PC 앱 화면을 긁는 GUI 자동화. 불안정하고 업데이트마다 깨짐 |

**핵심**: 카카오톡에는 **공식 Bot API가 없습니다.** Slack·텔레그램과 근본적으로 다릅니다.

**권고**: 수업 소통은 Slack으로 가고, 카카오는 쓰지 않습니다.
(학부모 소통은 이미 학원 기존 채널로 분리돼 있습니다 — 120)

굳이 카카오톡 느낌의 봇을 학생에게 보여주고 싶다면 **텔레그램**이 대안입니다.
공식 Bot API가 있고 무료이며 5분이면 붙습니다. 다만 **도구를 하나 더 늘리는 것**이므로
6주차 "내 봇 만들기"를 Slack으로 유지하는 편이 낫다고 봅니다.

## 5. 수업에서의 쓰임

| 주차 | 쓰임 |
|---|---|
| 2주 | 블라인드 테스트 후 **정체 공개** — "아까 그 답이 이 봇이었어요" |
| 3주~ | 상시. 궁금할 때 같은 질문을 여러 봇에 던져 비교 |
| 6주 | **학생이 자기 봇을 만들 때 참고 구조** — "선생님 봇도 이렇게 생겼어요" |
| 10주 | 리마인드 — "이 모델들 중 내 프로젝트에 쓸 게 있나" |

**6주차와의 연결이 특히 좋습니다.** 학생이 만드는 알림 봇과 이 모델 봇이 **같은 구조**
(이벤트 수신 → 처리 → 메시지 게시)라, 이미 쓰고 있던 것의 속을 열어 보는 자리가 됩니다.

## 7. 검증 기준

1. `@봇` 멘션 시 **3초 안에** "생각 중" 메시지가 뜬다
2. 답변이 **글자가 차오르듯** 갱신된다 (한 번에 통째로 뜨지 않음)
3. 같은 질문에 **중복 답변이 없다** (재전송 방지 확인)
4. 서버를 내린 상태에서 멘션 → **친절한 안내**가 뜨고 봇이 죽지 않는다
5. 6명이 동시에 물어도 큐잉되며 서버가 버틴다
6. 학생 계정에서 회사 서버 주소로 직접 접근 → **차단됨**
