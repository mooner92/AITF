## 1. Slack — 학생 gmail로 초대

### 계정 방침 — 학생 gmail 1개로 통일 (2026-08-19 확정)

**학생이 각자 Google 계정(gmail) 하나를 개강 전에 준비한다.** 이 하나로 전부 풀린다:

| 쓰이는 곳 | 무엇이 되나 |
|---|---|
| Slack | 워크스페이스 초대 |
| Gemini API | **학생별 무료 티어 키** — 학원 공유 키보다 한도가 6배 |
| 외부 접속(110) | Cloudflare Access OTP 인증 재가능 |
| n8n | 자기 키로 워크플로 구성 |

이전 안(강사 도메인 별칭 메일)은 폐기한다. gmail이 더 많은 것을 열어주고 관리 부담도 없다.

**대가 — 학부모 약속 두 개를 고쳐야 한다.**
"만들 계정 없음"과 "학생 이메일 수집 없음"이 더 이상 성립하지 않는다. 감추지 않고
안내문을 수정한다: 준비물 = 구글 계정 1개(가정에서 준비), 이메일은 수업 도구
초대·인증 용도로만 쓰고 수료 후 삭제.

**⚠ 만 14세 미만** — 한국에서 만 14세 미만은 보호자 동의(Family Link) 없이 Google 계정을
만들 수 없다. 중등반 저학년이 해당될 수 있으므로 **개강 안내문에 "보호자 동의가 필요할 수
있음"을 명시**하고, 준비가 안 된 학생을 위해 개강일에 학원 발급 예비 계정을 소수 준비해 둔다.

### 채널 구성 — 실제 워크스페이스 기준 (2026-08-26 생성 완료)

**워크스페이스 하나에 두 반을 넣고 채널로 가른다.** 워크스페이스를 반별로 쪼개면
Slack 앱이 워크스페이스 단위로 설치되므로 `/compare`·위키 알림·Hermes 의 앱·토큰·
프로세스가 전부 2벌이 된다. 하나면 봇 한 세트로 양쪽을 커버한다.

| 채널 | 상태 | 공개 | 용도 |
|---|---|---|---|
| `aitf-전체` | **생성됨** | 공개 | 공지·전체 소식. 강사가 주로 씀 |
| `high-class` | **생성됨** | 비공개 | 고등부 — 질문·잡담·봇 호출 |
| `middle-class` | **생성됨** | 비공개 | 중등부 — 〃 |
| `high-works` / `middle-works` | 3주차 전 | 비공개 | 작품 링크 갤러리 |
| 프로젝트 채널 | 10주차 | 비공개 | 주중 위임 작업 피드백 |

**작품 채널을 나누는 이유**: 매주 쌓이는 작품 링크가 대화에 묻히면 갤러리로 쓸 수 없다.
3주차부터 공개 결과물이 나오므로 그 전에 만든다.

**봇 전용 채널은 만들지 않는다.** 봇을 `high-class`·`middle-class` **양쪽에 초대**한다.
공용 봇 채널을 쓰면 **중등(14시) 블라인드 테스트의 정답이 고등(16시)에게 그대로 보인다** —
2주차 수업이 무너진다. 반별 채널 안에서 돌리면 서로 보이지 않는다.

- 멤버 목록에는 서로 보이므로 **표시 이름을 계정 ID로** 정하게 한다
  (1주차 계정 카드에 한 줄 추가)
- **초대는 금요일 리허설 때 일괄** (강사 결정) — 중등 gmail 미수집이라 차단 요소 아님

## 2. Notion — 주간 수업 정리 자동 발행

### 흐름

```
일 18:00 수업 종료
  → 20:00 서버 크론: 활동 수집 → 위키 md 생성 (v8 계획 3절, 기존 설계)
  → 20:30 요약 md → Notion 페이지 생성 (주차별 하위 페이지)
  → Slack #위키 채널에 링크 알림
```

**정본은 서버 위키(Gitea)다.** Notion은 읽기 좋은 발행본이며, 학생·학부모가 링크 하나로
복습하는 용도다. Notion이 죽어도 수업 데이터는 서버에 있다.

### 발행 구현 (2026-08-26 — `scripts/publish-notion.py`)

임커밋 레퍼런스(Claude Code Stop Hook → Notion DB)를 수업 단위로 번안했다:

| 레퍼런스 | 우리 번안 | 이유 |
|---|---|---|
| Stop Hook (대화 턴마다) | **일요일 20시 위키 cron** | 학생은 Codex 를 쓰고, 수업 단위가 주차다 |
| 속성: 작업/날짜/프로젝트/세션ID | 제목/날짜/**반(Select)**/주차/커밋/활동 학생 | 분류 축이 프로젝트가 아니라 반·주차 |
| 세션ID 로 같은 카드에 누적 | **(반, 주차) 키로 업서트** | 같은 주를 다시 돌려도 페이지가 늘지 않음(멱등) |
| 날짜별·프로젝트별 뷰 | 날짜별·**반별** 뷰 (Notion UI 에서 강사 1회 생성) | 그룹화 속성은 스크립트가 넣어 줌 |

- cron 은 `build-wiki.py && publish-notion.py` 순서 — 위키 생성이 실패하면 발행도 안 한다
- **토큰 미설정이면 조용히 생략** — Notion 이 없어도 위키는 항상 쌓인다 (LLM 비의존과 같은 원칙)
- 본문 블록은 raw JSON 에서 직접 생성 — 계정 ID만, 실명 없음
- DB 최초 생성은 스크립트가 하고(`NOTION_PARENT_PAGE` 필요), 이후 `NOTION_DB_ID` 재사용

**AI 가 쓴 서술이 Notion 까지 실려 간다 — 다만 봇이 쓰지는 않는다** (2026-08-26 확정)

```
enrich-wiki.py (LLM)  →  위키 md 마커 밖에 서술 작성  →  git 커밋으로 남음
                              ↓
publish-notion.py (결정적)  →  그 서술을 Notion 으로 운반
```

- **발행 경로에 모델을 두지 않는다.** LLM 은 git 으로 검토 가능한 위키 파일에만 쓰고,
  발행기는 운반만 한다. 지어내도 커밋에 남아 발견·수정이 되고, 정본은 서버 위키다
- 발행 시 **이번 주 새로 생긴 스킬·프로젝트**(지난주 raw 와 비교)를 추려 서술과 함께 싣는다.
  서술이 아직 없으면 이름만 나간다
- 마커 안(자동 생성 사실)은 싣지 않는다 — 이미 활동 목록으로 나가 있다

**봇(150)에 발행을 위임하지 않는 이유**: 발행이 Slack 연결·봇 생존·LLM 응답·
회사 서버 승인에 전부 의존하게 된다. 지금은 cron + Notion API 둘뿐이다.
가오리·거북이는 **알림과 질의응답**을 맡는다 — 발행 후 반별 위키 채널에 링크를
던지고, 학생이 "이번 주에 누가 뭐 만들었어?" 라고 물으면 답한다.

### 구축 순서 — 누가 뭘 하나

**강사가 직접 (계정 소유라 자동화 불가):**

1. **Slack 워크스페이스 생성** (slack.com/create) — 이름 예: `AITF`
   채널 4개: `#공지` `#질문` `#작품` `#모델비교` (+ 나중에 `#위키` `#프로젝트`)
2. **학생 초대** — roster 의 gmail 5건으로 (수집 완료 상태)
3. **Notion 워크스페이스**(또는 기존 계정에 페이지 하나) → "AITF 수업 기록" 페이지 생성
4. notion.so/profile/integrations → **내부 통합 생성** → 토큰 복사
5. 3의 페이지 우상단 ⋯ → 연결(Connections) → 4의 통합 추가
6. 서버에 토큰 저장:
   ```bash
   sudo tee -a /opt/scripts/.env <<'ENV'
   NOTION_TOKEN=⟪ntn_...⟫
   NOTION_PARENT_PAGE=⟪페이지 URL 끝의 32자리 ID⟫
   ENV
   sudo chmod 600 /opt/scripts/.env
   ```
7. 1회 실행해 DB 생성 확인: `sudo /opt/scripts/publish-notion.py --week 1`
   → 출력된 `NOTION_DB_ID=` 줄을 `.env` 에 추가
8. Notion UI 에서 뷰 2개 생성 — 날짜별(Day 그룹) · 반별(Select 그룹)

**서버가 자동 (구축 완료):**

- 일요일 20시 cron 체인: **위키 생성 → Notion 발행 → Slack 알림**
  (뒤 둘은 토큰·웹훅 미설정이면 조용히 생략. 위키 생성이 실패하면 뒤가 안 돈다)
- Slack 알림은 **반별 웹훅으로 각각** 보낸다 (`SLACK_WEBHOOK_HIGH`/`_MID`) —
  공용으로 보내면 반끼리 보이면 안 되는 것이 섞인다
- 알림 실패는 종료 코드 0 — 알림 때문에 체인 뒷단이 멈추지 않게
- 멱등 업서트라 재실행·백필(`--week N`) 자유

**다음 단계 (Slack 워크스페이스 생긴 뒤):**

- Slack 앱 생성(Socket Mode) → `#위키` 알림 봇 + `/compare` 봇 (150 과 뼈대 공유)
- 자동화에 MCP 는 쓰지 않는다 — 크론은 REST 직결(기존 결정). MCP 는 강사가
  대화로 Notion 을 다듬을 때만

### 위키는 세 개다 — 반별 2 + 통합 아카이브 1 (2026-08-24 확정)

| 위키 | 내용 | 열람 |
|---|---|---|
| **중등부 위키** (`class-wiki-mid`) | 중등반 학생·활동·그래프만 | 중등반 내부 |
| **고등부 위키** (`class-wiki-high`) | 고등반 학생·활동·그래프만 | 고등반 내부 |
| **통합 아카이브** (`class-archive`) | 두 반의 주차별 수업 기록·결과물 하이라이트 — 수업 자체의 기록 | 강사 (공개 범위는 원장 협의) |

- **이유**: 반이 섞이면 위키 그래프에 모르는 계정이 노드로 떠서 "저 사람 누구지"가
  집중을 깬다. 7주차 공개 장면도, 10주차 리마인드도 자기 반 것만 보여야 몰입이 산다.
- 반별 위키 2개는 060에서 이미 계정·저장소와 함께 생성하도록 설계돼 있고,
  **통합 아카이브가 이번에 추가된 것**이다. 자동 위키 크론이 학생 활동을 반별 위키에
  쓰고 나서, 반 구분 없는 수업 단위 요약(그 주 하이라이트·결과물 링크)을 아카이브에
  한 벌 더 쓴다 — 수집은 한 번, 출력만 세 갈래.
- Notion 주간 발행도 같은 구조를 따른다: 반별 페이지 2개 발행, 아카이브는 강사용.

### Notion 연동 설정 (두 가지 — 용도가 다르다)

**ⓐ 자동 발행(크론)은 MCP가 아니라 API 직결로 한다.**
MCP는 대화형 에이전트가 도구를 쓰는 프로토콜이라, 정해진 문서를 정해진 시간에 올리는
일에는 LLM도 MCP도 필요 없다. 스크립트가 REST API를 부르는 쪽이 실패 지점이 적다.

```
1. notion.so/profile/integrations → 새 내부 통합(Internal) 생성 → 토큰 발급
2. 발행 대상 페이지 우상단 ⋯ → 연결(Connections) → 방금 만든 통합 추가
3. 서버 크론 스크립트가 토큰으로 pages.create 호출 (토큰은 /opt/scripts/.env, 600)
```

**ⓑ 강사가 대화로 정리·수정할 때는 MCP를 쓴다.**

```bash
# Claude Code
claude mcp add notion --env NOTION_TOKEN=<토큰> -- npx -y @notionhq/notion-mcp-server
# Codex CLI — ~/.codex/config.toml
[mcp_servers.notion]
command = "npx"
args = ["-y", "@notionhq/notion-mcp-server"]
env = { NOTION_TOKEN = "<토큰>" }
```

이후 "이번 주 정리 페이지에서 3절만 더 풀어서 써줘" 같은 작업을 대화로 한다.

## 3. 모델 비교 봇 — 이 스택의 백미

학생들은 GPT·Gemini 챗만 써봤다. **같은 질문에 모델마다 다르게 답하는 것을 나란히 보는 것**이
"모델을 고른다"(3주차)를 몸으로 만든다.

### 구조

```
학생: /compare 김치찌개 레시피를 세 줄로
  → Slack 봇 (학원 서버에서 구동)
  ├─▶ 회사 서버 로컬 모델 (qwen · gemma)   ← Zero Trust 서비스 토큰
  └─▶ 학원 GPT 키 (luna)                   ← 기존 상한 안에서
  → 스레드에 모델별 답 + 응답 시간 + 예상 비용 나란히
```

- **학생은 회사 서버에 직접 닿지 않는다.** 봇 프로세스만 서비스 토큰을 갖고,
  토큰은 학원 서버의 봇 환경에만 있다 (Zero Trust Access 서비스 토큰 방식)
- 로컬 모델 호출은 **무료**라 부담 없이 쓰게 두고, GPT 경유는 봇이 횟수 제한
- 응답에 시간·비용을 같이 찍는다 — "빠르고 공짜인데 조금 어색함 vs 느리고 유료인데 매끄러움"이
  숫자로 보인다

### ⚠ 확인 필요

**회사 서버 자원을 수업에 쓰는 것은 회사 승인 사항이다.** 기술적으로 되는 것과 해도 되는 것은
다르다 — 사용량 상한·시간대·로그 정책을 회사와 합의한 뒤 붙인다. 승인 전까지 봇은
로컬 모델 없이 GPT 단독으로도 동작하게 만든다 (강등 경로).

## 4. Claude 디자인 체험 — 구독 연결은 하지 않는다

**개인 Claude 구독을 학생용 Slack에 연결하는 것은 권장하지 않는다.**
구독 약관상 계정 공유·제3자 사용에 해당할 소지가 있고, 학생 6명이 쓰면 강사 본인의
사용량 한도를 수업이 잠식한다.

**대안 (수업 시간 단체 세션)**: 프로젝터로 강사 계정을 띄우고 **반 전체가 지시문을 함께
만들어** 디자인을 뽑는다. 학생들이 문장을 제안 → 강사가 입력 → 결과를 같이 평가 → 수정.
"지시문이 디자인을 바꾼다"를 전원이 동시에 목격하는 구성이라 오히려 교육 효과가 크다.
같은 주제를 각자 Codex로 재현하는 것까지가 한 세트다 (디자인 스펙 스킬 활용).

GPT 쪽 대응물: Codex CLI 자체가 HTML/CSS 생성이 되므로 별도 도구가 필요 없다.

## 5. n8n — 셀프호스트라 무료다

**비용 걱정은 사실과 다르다.** 유료는 n8n Cloud이고, **셀프호스트는 무료**다(fair-code).
학원 서버 docker로 띄우면 라이선스 비용이 없다.

### 키 전략 — 학생별 Gemini 키 (계정 방침 확정으로 가능해짐)

학생이 gmail을 갖게 되었으므로 **각자 AI Studio에서 무료 키를 발급**한다.
학원 공유 키 1개보다 무료 한도가 인원수만큼 넓어져 대기 없이 실습할 수 있다.

- 키 발급 자체가 수업 소재다 — "API 키가 무엇인가, 왜 비밀인가"를 7주차 도입에서 다룬다
- 키는 각자 서버 홈의 환경 파일(600)에 넣는다. **공개 폴더·git에 넣으면 안 된다**는 것을
  함께 가르친다 (server-rules.md에 이미 있는 규칙)
- GPT 키는 학원 것을 소량만 — n8n 노드에서 호출 횟수를 워크플로 레벨에서 제한한다

### 체험 워크플로 (7주차 재료 후보)

"트리거 → AI → 결과가 눈에 보이는 곳"의 3단 구성이 좋다.

> **예: 아침 브리핑 봇** — 매일 9시 트리거 → 날씨 API(무료) → Gemini가 오늘의 한 줄 브리핑 +
> 나노바나나(Gemini 이미지)로 날씨 그림 생성 → Slack #공지에 전송

수업 후에도 매일 아침 결과가 도착하므로 "내가 만든 게 계속 돌아간다"는 감각이 남는다.
영상 생성(Higgsfield 등)은 **유료라 제외** — 영상은 8주차 ffmpeg 파이프라인으로 충분하다.

## 6. "친구들에게 보여줄 만한" 재료 풀

스킬 위크(5주)·프로젝트(9~12주) 재료 후보다. 전부 무료·브라우저 실행·자립 파일이라
작품관에 그대로 전시된다. **커리큘럼의 "재료는 교체 가능" 원칙에 따라 풀로 관리**하고
그때 반응 좋은 것을 쓴다.

| 재료 | 무엇이 나오나 | 왜 통하나 |
|---|---|---|
| **three.js 3D 명함** | 마우스로 돌리는 3D 이름·오브젝트 | 첫 반응이 가장 큰 "우와" 계열 |
| **p5.js 제너러티브 아트** | 내 이름을 시드로 한 나만의 무늬 | 전원이 다른 결과 — 비교하는 재미 |
| **Tone.js 비트메이킹** | 브라우저에서 도는 나만의 비트 | 소리는 공유성이 가장 강함. 8주차 영상 BGM으로 연결 |
| **위키 그래프 시각화** | 우리 반 학습 지도 (이미 계획됨) | 자기가 노드로 들어 있음 |
| **QR 스티커** | 작품관 링크 QR 인쇄 | 폰으로 찍는 순간 오프라인 공유가 됨 |
