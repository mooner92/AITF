# 110 — 학생 웹서비스 포트와 외부 접속

**단계** P10 · **의존** [030](030-access.md)(터널·Access), [040](040-accounts.md)(계정)
**상태** `Draft` — 운영자 승인 대기 (방화벽 규칙 · 이메일 수집 여부)

## 목표

9주차부터 학생이 자기 웹서비스(개발 서버)를 띄우고, **10~12주차에는 학원 밖에서도**
자기 서비스와 터미널에 접속해 프로젝트를 이어갈 수 있게 한다.

전제 두 가지를 지킨다.

1. **서버에 새로 여는 인바운드 포트는 0개** — 지금의 잠금 상태를 그대로 유지한다
2. **한 학생의 서비스가 다른 학생이나 서버 전체에 영향을 주지 않는다**

---

## 설계

### 1. 외부 엔드포인트는 하나뿐이다

"학생마다 포트를 열어줘야 하나"에 대한 답은 **아니오**다.

```
인터넷 ──▶ Cloudflare (Access 인증)
              │
              ▼  터널 (아웃바운드 연결 — 서버는 인바운드를 열지 않는다)
         cloudflared
              │
              ▼
          nginx 127.0.0.1:8081
              │
   ┌──────────┼──────────────┬─────────────┐
   ▼          ▼              ▼             ▼
 /pages/    /git/         /monweb    학생 서비스
 (정적)    (Gitea)     (OpenObserve)  127.0.0.1:1NN00
```

서버가 외부에 노출하는 포트는 **여전히 0개**다. `cloudflared`가 밖으로 연결을 걸어
터널을 유지하고, 모든 트래픽이 그 터널로만 들어온다.
→ **방화벽에 새로 열 규칙이 없다.** 오히려 아무것도 열지 않는 것이 이 설계의 핵심이다.

### 2. 학생별 포트 대역

학생 한 명에게 **100개 대역**을 준다. 웹 하나만 띄우는 게 아니라 백엔드·DB·핫리로드까지
같이 뜨기 때문이다.

| 반 | 계정 | 대역 | 공개 포트 |
|---|---|---|---|
| 중등 | `mid01` | 11100 – 11199 | **11100** |
| 중등 | `mid02` | 11200 – 11299 | **11200** |
| … | | | |
| 고등 | `high01` | 12100 – 12199 | **12100** |
| 고등 | `high02` | 12200 – 12299 | **12200** |

공식: 중등 `11000 + N×100`, 고등 `12000 + N×100` (N = 계정 번호)

**대역 안에서 밖으로 나가는 것은 첫 번째 포트 하나뿐이다.** 나머지 99개는 내부 통신용이며
외부에서 접근할 수 없다. 학생이 백엔드를 11101에 띄우고 프론트가 그걸 부르는 구조는
그대로 동작하고, 외부에는 11100만 보인다.

### 3. 주소는 서브도메인으로 준다 — 경로가 아니라

`<BASE_DOMAIN>/app/mid01/` 같은 경로 방식을 **채택하지 않는다.**

이유: Vite·Next·CRA 같은 개발 서버는 자기가 사이트 루트에 있다고 가정하고
`/assets/app.js` 같은 **절대경로**를 뱉는다. 하위 경로로 서비스하려면 `base`/`basePath`를
매번 맞춰야 하고, 핫리로드 웹소켓 경로까지 어긋난다. **중학생이 매주 이걸 맞추는 것은 무리다.**

```
mid01.<BASE_DOMAIN>  ──▶  nginx (server_name 매칭)  ──▶  127.0.0.1:11100
high01.<BASE_DOMAIN> ──▶  nginx                     ──▶  127.0.0.1:12100
```

서브도메인이면 학생 서버는 자기가 루트에 있다고 믿어도 되고, 쿠키·CORS 경계도
학생별로 자연히 분리된다.

**와일드카드(`*.aitf...`) 대신 계정 수만큼 명시적 레코드를 만든다.** 와일드카드 프록시는
플랜에 따라 제약이 있고, 12개는 스크립트로 한 번에 만들면 끝이다.

### 4. nginx를 중간에 두는 이유

터널이 학생 포트로 직접 갈 수도 있지만 nginx를 거치게 한다.

- **학생이 서버를 안 켰을 때 안내 페이지를 준다.** 날것의 502 대신
  "아직 서버를 켜지 않았어요. 터미널에서 `npm run dev` 를 실행해 보세요"를 띄운다.
  수업 중 질문의 상당수가 여기서 사라진다
- 접근 로그가 한곳에 모여 관측(070)에 그대로 들어간다
- 업로드 크기·타임아웃 상한을 걸 수 있다

```nginx
server {
    listen 127.0.0.1:8081;
    server_name mid01.<BASE_DOMAIN>;

    location / {
        proxy_pass http://127.0.0.1:11100;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;      # 핫리로드 웹소켓
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 300s;
        client_max_body_size 20m;

        proxy_intercept_errors on;
        error_page 502 503 504 = /_offline;
    }
    location = /_offline { root /srv/fallback; try_files /offline.html =503; }
}
```

### 5. 학생 간 격리 — 정직하게

같은 호스트에서 도는 이상 `mid01`이 `curl 127.0.0.1:11200`으로 `mid02`의 서비스에
접근할 수 있다. **완전한 격리가 아니다.**

세 단계로 나눠 대응한다.

| 층 | 수단 | 상태 |
|---|---|---|
| 외부 | 인바운드 0 + Cloudflare Access | **적용됨** |
| 파일 | 홈 700, 계정 분리 | **적용됨** (040) |
| 프로세스 간 | iptables `owner` 모듈로 대역 밖 접속 차단 | **승인 대기** |

```bash
# 각 학생은 자기 대역에만 접속할 수 있다 (설계안 — 미적용)
iptables -A OUTPUT -o lo -p tcp --dport 11200:11299 \
         -m owner ! --uid-owner mid02 -j REJECT
```

> **방화벽 변경은 운영자 확인 후 적용한다.** 미적용 상태에서도 외부 노출 위험은 없고,
> 학생 간 접근은 학습 서버 특성상 실질 피해가 크지 않다. 그러나 "막혀 있다"고
> 말하지는 않는다 — 규칙(AGENTS.md)과 약속으로 다루고, 한계를 문서에 남긴다.

### 6. 외부 접속 개방 (10~12주차) — 이메일 없이

**결론: 이메일을 받지 않는다.** 학부모께 드린 "이메일 불필요" 안내를 그대로 지킬 수 있다.

이유는 단순하다. **학생은 이미 ID와 비밀번호를 갖고 있다** — 계정 생성(040) 때 발급한
`mid01` / 비밀번호다. 외부 접속에도 이걸 그대로 쓰면 새로 만들 것도, 외울 것도, 받을 것도 없다.

#### 4겹으로 막는다

| 겹 | 수단 | 막는 것 | 비용 |
|:--:|---|---|---|
| 1 | **국가 제한 (KR만)** | 자동화 공격의 대부분 | Cloudflare 규칙 1개 |
| 2 | **요청 속도 제한** | 비밀번호 무차별 대입 | Cloudflare 규칙 1개 |
| 3 | **계정 인증** | 남이 내 서비스에 들어오는 것 | nginx `auth_basic` |
| 4 | **fail2ban** | 반복 실패 IP 차단 | 서버 설정 |

1겹만으로도 인터넷 배경 공격의 대부분이 사라진다. 서버를 통째로 여는 게 아니라
**여전히 터널 하나만 열려 있고, 그 앞에 문을 네 개 두는 것**이다.

#### 계정 인증을 붙이는 방법

계정 생성 시 같은 비밀번호로 `htpasswd` 항목을 함께 만든다. 학생은 터미널에 들어갈 때와
**똑같은 ID·비밀번호**를 브라우저에서 한 번 입력한다.

```nginx
# 학원 IP는 그냥 통과, 그 외에는 계정 인증
geo $academy { default 0; <ACADEMY_IP>/32 1; }

server {
    server_name mid01.<BASE_DOMAIN>;
    satisfy any;
    allow <ACADEMY_IP>;              # 학원에서는 인증 없이
    deny  all;
    auth_basic "AITF";               # 밖에서는 계정 인증
    auth_basic_user_file /etc/nginx/aitf.htpasswd;
    location / { proxy_pass http://127.0.0.1:11100; }
}
```

#### 무엇을 잃는가 — 정직하게

Cloudflare Access OTP보다 **약하다.** 비밀번호가 유출되면 그 학생 계정이 열린다.
다만 실질 피해가 제한적인 이유가 있다.

- 서버에 개인정보·금전 정보가 없다 (이메일조차 안 받으므로)
- 학생 계정에 `sudo`가 없다 — 서버를 망가뜨릴 수 없다
- 계정별로 파일이 격리돼 있다 (040)
- 매주 스냅샷이 있어 되돌릴 수 있다 (080)
- 유출이 의심되면 비밀번호 하나만 바꾸면 끝난다

**교육 과정 서버에 필요한 수준으로는 충분하다**고 판단한다.
더 강하게 가려면 그때 Access OTP를 얹으면 되고, 그건 이메일을 받기로 결정한 뒤의 이야기다.

#### 시점

| 시점 | 상태 |
|---|---|
| 1~9주 | 학원 IP에서만. 밖에서는 아예 안 열림 |
| 10~12주 | 위 4겹을 켜고 외부 개방 |
| 수료 후 | 즉시 차단, 계정 정지 |

## 앞선 결정과의 정합성 — 해소됨

초안에서는 Cloudflare Access OTP를 전제해 **이메일 수집이 필요**했고, 이는
[`academy-request.md`](../curriculum/academy-request.md)의 "이메일 불필요" 안내와 충돌했다.

**계정 인증 방식으로 바꾸면서 이 충돌이 사라졌다.** 학부모께 드린 안내를 바꾸지 않아도 되고,
운영자 승인 항목도 하나 줄었다. 관련 문서의 이메일 수집 항목은 되돌렸다.

## 검증 기준

1. `ss -tlnp` 결과에 **0.0.0.0 바인딩이 없다** (또는 있어도 인바운드가 막혀 외부 접근 불가)
2. 학생 서버를 끈 상태에서 자기 주소 접속 시 **502가 아니라 안내 페이지**가 뜬다
3. 학원 IP에서 접속 시 **로그인 화면 없이** 바로 열린다
4. 외부 IP에서 접속 시 계정 인증을 요구하고, 틀린 비밀번호를 반복하면 차단된다
8. 한국 밖 IP에서는 아예 도달하지 않는다
5. 핫리로드(웹소켓)가 서브도메인 주소에서 동작한다
6. (격리 적용 시) `mid01`이 `127.0.0.1:11200`에 접속하면 거부된다
7. 6명이 동시에 개발 서버를 띄웠을 때 메모리·CPU가 상한 안에 있다 — **미측정**
